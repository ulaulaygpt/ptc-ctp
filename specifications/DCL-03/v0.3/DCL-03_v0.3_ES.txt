Principio rector

DCL-03 protege una declaración pública y permite regenerar exactamente notice.txt. No demuestra que la declaración sea verdadera, que el aviso se mostrara efectivamente al público ni que una URL permanezca disponible en el futuro.

Mapa del documento

DCL-03 define qué se declara, cómo se compone con FRS-01, qué texto visible se deriva, qué puede verificar Validator y dónde terminan sus afirmaciones.

PARTE I · Alcance y significado

1. Propósito

DCL-03 define un bloque textual que declara una intervención de inteligencia artificial sobre un archivo y una derivación pública legible de esa declaración. El bloque se integra en el mismo objeto canónico que la referencia exacta del archivo.

2. Alcance

Gramática de PTC DISCLOSURE.

Valores cerrados de type y tratamiento de language.

Reglas de verification_url.

Composición con file-reference-sha256-v1.

Derivación byte a byte de PUBLIC_NOTICE/notice.txt.

Requisitos de generación para notice.html, notice.svg y qr.svg.

Estados independientes de divulgación.

Integración con PKG-02 y sus vectores.

3. Fuera de alcance

Determinar automáticamente si un contenido fue generado o modificado con IA.

Clasificar jurídicamente un contenido como deepfake o certificar cumplimiento normativo.

Demostrar que el aviso fue mostrado en la primera exposición o en una plataforma concreta.

Garantizar disponibilidad, persistencia o contenido futuro de verification_url.

Alojar el paquete, crear una página pública o reservar un DOI.

Aplicar disclosure-notice-v1 directamente a contenido textual ordinario.

Definir diseño gráfico obligatorio o comparar byte a byte HTML, SVG o QR.

4. Referencias

PARTE II · Gramática y composición

8. Alcance de composición

En la versión 1, disclosure-notice-v1 DEBE aparecer únicamente como segundo bloque de un objeto canónico cuyo primer bloque sea conforme a file-reference-sha256-v1.

NO DEBE aparecer de forma aislada.

NO DEBE anexarse directamente a un objeto canónico textual ordinario.

DEBE aparecer una sola vez.

DEBE ir después de PTC FILE REFERENCE.

Entre ambos bloques DEBE existir exactamente una línea vacía.

El único bloque PTC se añade después del objeto compuesto completo.

9. Forma normativa

PTC DISCLOSURE
profile: disclosure-notice-v1
type: <tipo>
language: <idioma>
verification_url: <URL HTTPS>

La línea verification_url es opcional. Cuando se omite, language es la última línea. El bloque termina siempre en exactamente un LF.

9.1 Gramática compacta

disclosure = header LF profile-line LF type-line LF language-line [url-line LF]
header = "PTC DISCLOSURE"
profile-line = "profile: disclosure-notice-v1"
type-line = "type: " disclosure-type
language-line = "language: " language-token
url-line = "verification_url: " https-uri
disclosure-type = "ai_generated" / "ai_modified" / "ai_generated_or_modified"
language-token = 2*8LOWALPHA
LOWALPHA = %x61-7A
LF = %x0A

9.2 Reglas byte a byte

Codificación UTF-8 sin BOM.

Orden fijo de campos.

Exactamente un espacio ASCII después de cada dos puntos.

Sin tabulaciones, espacios iniciales, espacios finales ni líneas adicionales.

No se permiten campos desconocidos dentro de disclosure-notice-v1.

No se permite repetir type, language o verification_url.

Un bloque duplicado o en posición incorrecta produce ROJO en divulgación.

10. Valores de type

Valor

Significado declarado

ai_generated

El operador declara que el contenido fue generado con IA.

ai_modified

El operador declara que el contenido fue modificado con IA.

ai_generated_or_modified

El operador declara generación o modificación con IA sin separar ambas posibilidades.

type no expresa intensidad, porcentaje, autoría jurídica, deepfake, engaño ni cumplimiento normativo. Un valor desconocido produce ROJO en el eje de divulgación.

Validator NO DEBE realizar una comparación semántica entre type y el campo purpose del PTC. Ambos valores se verifican en sus respectivas estructuras, pero una aparente contradicción narrativa entre ellos no produce por sí sola ROJO ni autoriza a inferir la verdad material de la declaración.

11. Valores de language

La versión 1 admite es, en y fr. language identifica la plantilla de notice.txt, no el idioma del archivo fuente.

Valor

12. verification_url

Es opcional.

DEBE ser una URL HTTPS absoluta con host no vacío.

DEBE estar representada en ASCII; dominios internacionales usan punycode y otros caracteres se codifican por porcentaje.

NO DEBE contener usuario, contraseña, espacios, CR, LF ni caracteres de control.

NO DEBE superar 2048 bytes UTF-8.

Puede incluir puerto, ruta, consulta y fragmento.

Cambiar cualquier carácter de la URL modifica el objeto canónico y exige generar un PTC nuevo.

URL declarada no equivale a URL disponible

Una URL reservada para una publicación futura puede ser válida aunque todavía no responda. La sintaxis pertenece al objeto protegido; la disponibilidad es una comprobación temporal e informativa.

13. Objeto canónico compuesto

PTC FILE REFERENCE
profile: file-reference-sha256-v1
size_bytes: <decimal>
source_sha256: <64 hex minúsculas>

PTC DISCLOSURE
profile: disclosure-notice-v1
type: <tipo>
language: <idioma>
[verification_url: <URL HTTPS>]

El objeto compuesto termina en un LF. El PTC se añade inmediatamente después, conforme a R-01. La línea vacía entre los dos bloques forma parte del objeto protegido.

14. Retroactividad del hash

Orden obligatorio

El aviso DEBE decidirse e incorporarse antes de calcular hash_doc_sha256. Añadir, eliminar o modificar PTC DISCLOSURE después de generar el PTC cambia el objeto canónico y exige una nueva declaración.

PARTE III · Generación y verificación

15. Algoritmo de generación

1. Cerrar la versión final del archivo fuente.

2. Generar PTC FILE REFERENCE conforme a FRS-01.

3. Recoger type, language y, opcionalmente, verification_url.

4. Validar valores, sintaxis y límites.

5. Construir PTC DISCLOSURE con la gramática exacta.

6. Componer ambos bloques con una única línea vacía.

7. Calcular hash_doc_sha256 sobre el objeto compuesto normalizado.

8. Generar el único PTC conforme a PTC-F.

9. Derivar notice.txt exactamente.

10. Generar los artefactos de presentación permitidos.

11. Construir el paquete conforme a PKG-02.

16. Algoritmo de verificación

1. Verificar el PTC y hash_doc_sha256 conforme a R-01/PTC-F.

2. Confirmar que el primer bloque satisface FRS-01.

3. Localizar el segundo bloque en la posición exacta.

4. Validar cabecera, orden, campos, type y sintaxis de language y URL.

5. Determinar si language está soportado.

6. Regenerar notice.txt desde type, language y verification_url.

7. Comparar notice.txt byte a byte.

8. Comprobar opcionalmente disponibilidad de verification_url.

9. Inspeccionar la presencia de artefactos de presentación conforme a PKG-02. Decodificar el contenido de qr.svg es opcional para el verificador; si lo hace y obtiene una URL distinta de verification_url, DEBE emitir ROJO en el eje del paquete sin alterar por esa sola causa el resultado independiente de divulgación.

10. Emitir divulgación como eje separado.

17. Separación de resultados

Declaración PTC:        VERDE / ROJO
Archivo fuente:         VERDE / ÁMBAR / ROJO
Estructura del paquete: VERDE / ÁMBAR / ROJO
Divulgación pública:    VERDE / ÁMBAR / ROJO

DCL-03 NO DEBE crear un veredicto global ni aplicar «prevalece el peor». Una URL temporalmente inaccesible no convierte en falso un PTC válido; un notice.txt modificado no altera por sí mismo los bytes de la fuente.

El eje de divulgación DEBE mostrarse únicamente cuando exista PTC DISCLOSURE o cuando se detecte un intento reconocible de divulgación, como un bloque malformado, public_notice en manifest.json o entradas bajo PUBLIC_NOTICE/.

Cuando no exista ningún bloque ni artefacto de divulgación, la interfaz DEBE omitir este eje. PUEDE mostrar, fuera del sistema de semáforos, la indicación neutral «Sin aviso público». Esta omisión no crea un cuarto estado y no constituye ÁMBAR.

ÁMBAR queda reservado para intentos reconocibles de divulgación que no pueden resolverse completamente, como un idioma bien formado pero no soportado o una comprobación externa no disponible.

PARTE IV · notice.txt normativo

18. Función

PUBLIC_NOTICE/notice.txt es el único artefacto derivado cuya igualdad byte a byte forma parte del eje de divulgación. Se genera exclusivamente a partir de type, language y verification_url.

19. Serialización exacta

Sin verification_url:

<TÍTULO>
LF
<CUERPO>
LF

Con verification_url:

<TÍTULO>
LF
<CUERPO>
LF
<ETIQUETA_URL>: <verification_url>
LF

UTF-8 sin BOM.

Exactamente una línea vacía entre título y cuerpo.

Cuando existe URL, exactamente una línea vacía entre cuerpo y línea de verificación.

Sin espacios finales.

Exactamente un LF final.

No se añaden profile, type, language, fecha, hash ni explicaciones técnicas.

22. Cambio de plantillas

Las cadenas anteriores forman parte de disclosure-notice-v1. Corregir puntuación, estilo o traducción cambiaría notice.txt y requeriría una nueva versión del perfil. Un verificador de v1 DEBE conservar estas cadenas.

PARTE V · Presentación e integración con PKG-02

23. notice.html y notice.svg

Son artefactos de presentación, no autoridades criptográficas.

Un generador conforme DEBE mostrar el mismo título y cuerpo semántico que notice.txt.

PUEDE cambiar diseño, tipografía, dimensiones, accesibilidad y estilos.

Un verificador NO DEBE exigir igualdad byte a byte ni hacer rojo el eje de divulgación por diferencias visuales.

Una contradicción obvia detectada PUEDE mostrarse como advertencia de paquete o presentación.

24. qr.svg

Solo se genera cuando existe verification_url.

Un generador conforme DEBE codificar únicamente la cadena exacta de verification_url.

NO DEBE introducir texto, identificadores, hashes ni datos de seguimiento dentro del QR.

La ausencia de QR cuando existe URL es una incidencia de paquete conforme a PKG-02.

Modificar los bytes o el estilo del QR no invalida por sí mismo el eje de divulgación.

Si un verificador decide decodificar qr.svg y obtiene una URL distinta de verification_url, DEBE emitir ROJO en el eje del paquete por contradicción con un artefacto autoritativo. El eje de divulgación continúa dependiendo del bloque protegido y de notice.txt.

25. Carpeta PUBLIC_NOTICE/

PUBLIC_NOTICE/
    README.txt
    notice.txt
    notice.html
    notice.svg
    qr.svg       # solo con verification_url

La presencia de PTC DISCLOSURE, public_notice en manifest.json y PUBLIC_NOTICE/ DEBE ser coherente conforme a PKG-02.

La coherencia entre los archivos presentes en PUBLIC_NOTICE/ y las rutas declaradas en public_notice se rige por PKG-02.

Los archivos adicionales no alteran por sí solos el eje de divulgación. Una entrada adicional segura puede producir ÁMBAR en el eje del paquete y una entrada peligrosa, ambigua o contradictoria puede producir ROJO en ese eje, conforme a PKG-02.

26. Objeto public_notice

{
  "public_notice": {
    "profile": "disclosure-notice-v1",
    "readme_path": "PUBLIC_NOTICE/README.txt",
    "notice_path": "PUBLIC_NOTICE/notice.txt",

28. Disponibilidad de URL

La comprobación de red es opcional.

CORS, modo sin conexión, DNS, TLS o fallo temporal NO DEBEN invalidar el PTC.

Una respuesta HTTP no demuestra que la página muestre el paquete correcto.

Una URL reservada puede permanecer ámbar hasta la publicación.

Una respuesta 301, 302, 307 o 308 hacia un destino distinto se registra como información de disponibilidad o como ÁMBAR operativo. La redirección no modifica el objeto protegido ni el eje de divulgación.

El destino final de una redirección NO DEBE sustituir silenciosamente a verification_url ni considerarse criptográficamente equivalente.

Validator NO DEBE afirmar persistencia futura.

29. Exposición efectiva

Límite no resoluble por el paquete

DCL-03 puede demostrar que existía un aviso protegido y que notice.txt lo representaba correctamente. No puede demostrar que una plataforma, institución o persona lo mostrara en el momento debido.

30. Copias transformadas por plataformas

Una plataforma puede recomprimir una imagen o recodificar un vídeo. FRS-01 identifica el original conservado; el aviso y la URL mantienen trazabilidad pública. Validator NO DEBE afirmar que los bytes reproducidos por la plataforma coinciden con el original salvo comprobación independiente.

31. Seguridad y privacidad

verification_url se hace pública dentro del bloque, notice.txt, HTML, SVG y QR.

La URL NO DEBERÍA contener tokens secretos, datos personales innecesarios ni identificadores temporales.

Los artefactos HTML NO DEBEN incluir scripts, rastreadores ni recursos remotos por defecto.

El QR NO DEBE codificar nada distinto de la URL.

La comprobación de URL DEBERÍA evitar enviar el archivo fuente o el PTC a terceros.

32. Compatibilidad

Un Validator nuevo DEBE seguir verificando paquetes sin divulgación.

Un verificador que no conozca disclosure-notice-v1 puede verificar PTC como texto, pero no el eje de divulgación.

Un profile desconocido produce ÁMBAR de divulgación, no invalidez automática del PTC.

Cambios futuros en HTML, SVG o bibliotecas QR no deben volver rojos paquetes antiguos.

Una futura divulgación textual ordinaria requerirá otro perfil y no modifica v1.

37. Pruebas mínimas de interoperabilidad

Dos generadores producen el mismo bloque y notice.txt para las nueve combinaciones type × language.

Dos verificadores obtienen los mismos estados para todos los vectores negativos.

Los ZIP físicos DCL-V01 y DCL-V02 se abren conforme a PKG-02.

La ausencia de URL omite simultáneamente verification_url, qr_path y qr.svg.

Cambiar solo HTML, SVG o QR no cambia hash_doc_sha256 ni el resultado de notice.txt.

La URL declarada permanece distinguida de su disponibilidad.

Un QR divergente produce ROJO de paquete y no se trata como una simple diferencia visual.

Una redirección HTTP se registra como comportamiento remoto temporal y no reescribe verification_url.

Ningún resultado de divulgación colapsa PTC, fuente o paquete.

Dos interfaces omiten por igual el eje de divulgación cuando la función nunca fue invocada.

Un intento reconocible sin PTC DISCLOSURE produce el mismo ROJO de divulgación en todos los verificadores.

Los archivos adicionales de PUBLIC_NOTICE/ afectan al eje del paquete conforme a PKG-02, sin modificar por sí solos el resultado de notice.txt.

38. Preguntas cerradas para revisión hostil

1. ¿Las tres cadenas de type son suficientemente claras y no introducen una clasificación jurídica implícita?

2. ¿El tratamiento de language desconocido como ÁMBAR es compatible con una lista de idiomas cerrada?

3. ¿La gramática de verification_url es suficientemente precisa para implementaciones independientes?

4. ¿Debe prohibirse el fragmento de URL para evitar destinos no equivalentes o es correcto permitirlo?

5. ¿La derivación exacta de notice.txt cubre todos los finales de línea y espacios relevantes?

6. ¿La diferencia entre requisitos del generador y comprobaciones obligatorias del verificador para HTML, SVG y QR está suficientemente clara?

7. ¿Decodificar un QR con URL divergente debe seguir siendo advertencia o debería producir ROJO de paquete?

8. ¿La omisión del eje cuando no existe ningún intento de divulgación conserva correctamente el vocabulario de tres estados sin ocultar una anomalía real?

9. ¿DCL-V01 y DCL-V02 publican suficientes preimágenes para reproducir los PTC sin depender del ZIP físico?

10. ¿Falta algún vector sobre URLs reservadas, indisponibles, redirecciones o contenido remoto cambiado?

39. Resolución de la revisión hostil v0.1

Claude Sonnet 5 verificó computacionalmente las nueve plantillas y los dos vectores físicos, incluido el contenido real del QR de DCL-V01. No detectó discrepancias en los valores publicados.

La decodificación del QR permanece opcional para el verificador.

Una URL QR divergente se eleva a ROJO del eje del paquete, sin colapsar el eje de divulgación.

Los campos, ptc.txt y preimágenes exactas de DCL-V01 y DCL-V02 se publican dentro de la especificación.

Se añade el caso de redirección HTTP como comprobación externa informativa.

En v0.2 se mantuvieron sin cambios type, language, fragmentos URL y todas las plantillas normativas. El tratamiento de la ausencia total de divulgación se revisa posteriormente en §40.

40. Resolución del control independiente v0.2

DeepSeek consideró DCL-03 v0.2 técnicamente sólido y señaló cuatro posibles mejoras. Claude Sonnet 5 contrastó cada una contra el documento real.

Se descarta la supuesta ausencia de tamaños en §35: la tabla ya publica los nueve tamaños en bytes.

Se incorpora la remisión explícita a PKG-02 para archivos adicionales dentro de PUBLIC_NOTICE/.

Se declara expresamente que purpose y type no se comparan semánticamente.

Se acepta el diagnóstico sobre la ausencia total de divulgación, pero no se crea un cuarto estado: cuando la función nunca se invocó, el eje se omite y puede mostrarse una indicación neutral fuera del semáforo.

ÁMBAR queda reservado para intentos reconocibles no resueltos; un intento sin PTC DISCLOSURE produce ROJO.

No se modifican las nueve plantillas, los dos vectores físicos, las preimágenes ni los hashes publicados.

A.3 Síntesis

Diferencia esencial

DCL-03 no convierte una afirmación en verdad. Convierte una afirmación pública en un objeto preciso, vinculado, reproducible y verificable, y conserva el límite entre declarar, mostrar y demostrar.
