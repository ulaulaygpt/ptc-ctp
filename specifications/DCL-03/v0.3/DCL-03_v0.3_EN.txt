Governing principle

DCL-03 protects a public declaration and makes it possible to regenerate notice.txt exactly. It does not demonstrate that the declaration is true, that the notice was actually shown to the public, or that a URL will remain available in the future.

Document map

DCL-03 defines what is declared, how it is composed with FRS-01, which visible text is derived, what Validator can verify, and where its claims end.

PART I · Scope and meaning

1. Purpose

DCL-03 defines a textual block declaring an artificial-intelligence intervention on a file and a human-readable public derivation of that declaration. The block is integrated into the same canonical object as the exact file reference.

2. Scope

Grammar of PTC DISCLOSURE.

Closed values of type and treatment of language.

Rules for verification_url.

Composition with file-reference-sha256-v1.

Byte-for-byte derivation of PUBLIC_NOTICE/notice.txt.

Generation requirements for notice.html, notice.svg, and qr.svg.

Independent disclosure states.

Integration with PKG-02 and its vectors.

3. Out of scope

Automatically determining whether content was generated or modified with AI.

Legally classifying content as a deepfake or certifying regulatory compliance.

Demonstrating that the notice was shown on first exposure or on a particular platform.

Guaranteeing availability, persistence, or future content of verification_url.

Hosting the package, creating a public page, or reserving a DOI.

Applying disclosure-notice-v1 directly to ordinary textual content.

Defining a mandatory graphic design or comparing HTML, SVG, or QR byte for byte.

PART II · Grammar and composition

8. Composition scope

In version 1, disclosure-notice-v1 MUST appear only as the second block of a canonical object whose first block conforms to file-reference-sha256-v1.

MUST NOT appear in isolation.

MUST NOT be appended directly to an ordinary textual canonical object.

MUST appear exactly once.

MUST come after PTC FILE REFERENCE.

Exactly one blank line MUST exist between the two blocks.

The single PTC block is appended after the complete composite object.

9. Normative form

PTC DISCLOSURE
profile: disclosure-notice-v1
type: <type>
language: <language>
verification_url: <HTTPS URL>

The verification_url line is optional. When omitted, language is the last line. The block always ends in exactly one LF.

9.1 Compact grammar

disclosure = header LF profile-line LF type-line LF language-line [url-line LF]
header = "PTC DISCLOSURE"
profile-line = "profile: disclosure-notice-v1"
type-line = "type: " disclosure-type
language-line = "language: " language-token
url-line = "verification_url: " https-uri
disclosure-type = "ai_generated" / "ai_modified" / "ai_generated_or_modified"
language-token = 2*8LOWALPHA
LOWALPHA = %x61-7A
LF = %x0A

9.2 Byte-for-byte rules

UTF-8 encoding without BOM.

Fixed field order.

Exactly one ASCII space after each colon.

No tabs, leading spaces, trailing spaces, or additional lines.

Unknown fields are not permitted within disclosure-notice-v1.

type, language, or verification_url may not be repeated.

A duplicated block or a block in the wrong position produces RED on the disclosure axis.

10. type values

Value

Declared meaning

ai_generated

The operator declares that the content was generated with AI.

ai_modified

The operator declares that the content was modified with AI.

ai_generated_or_modified

The operator declares AI generation or modification without distinguishing between the two possibilities.

type does not express intensity, percentage, legal authorship, deepfake status, deception, or regulatory compliance. An unknown value produces RED on the disclosure axis.

Validator MUST NOT perform a semantic comparison between type and the PTC purpose field. Both values are verified within their respective structures, but an apparent narrative contradiction between them does not by itself produce RED or authorize an inference about the material truth of the declaration.

11. language values

Version 1 supports es, en, and fr. language identifies the notice.txt template, not the language of the source file.

Other well-formed token

12. verification_url

It is optional.

MUST be an absolute HTTPS URL with a non-empty host.

MUST be represented in ASCII; internationalized domains use punycode and other characters are percent-encoded.

MUST NOT contain username, password, spaces, CR, LF, or control characters.

MUST NOT exceed 2048 UTF-8 bytes.

May include a port, path, query, and fragment.

Changing any character of the URL changes the canonical object and requires generation of a new PTC.

Declared URL is not the same as available URL

A URL reserved for a future publication may be valid even if it does not yet respond. Syntax belongs to the protected object; availability is a temporary and informative check.

13. Composite canonical object

PTC FILE REFERENCE
profile: file-reference-sha256-v1
size_bytes: <decimal>
source_sha256: <64 lowercase hex>

PTC DISCLOSURE
profile: disclosure-notice-v1
type: <type>
language: <language>
[verification_url: <HTTPS URL>]

The composite object ends in one LF. The PTC is appended immediately afterwards, in accordance with R-01. The blank line between the two blocks is part of the protected object.

14. Retroactivity of the hash

Required order

The notice MUST be decided and incorporated before calculating hash_doc_sha256. Adding, removing, or modifying PTC DISCLOSURE after generating the PTC changes the canonical object and requires a new declaration.

PART III · Generation and verification

15. Generation algorithm

1. Freeze the final version of the source file.

2. Generate PTC FILE REFERENCE in accordance with FRS-01.

3. Collect type, language and, optionally, verification_url.

4. Validate values, syntax, and limits.

5. Construct PTC DISCLOSURE using the exact grammar.

6. Compose both blocks with a single blank line.

7. Calculate hash_doc_sha256 over the normalized composite object.

8. Generate the single PTC in accordance with PTC-F.

9. Derive notice.txt exactly.

10. Generate the permitted presentation artefacts.

11. Build the package in accordance with PKG-02.

16. Verification algorithm

1. Verify the PTC and hash_doc_sha256 in accordance with R-01/PTC-F.

2. Confirm that the first block satisfies FRS-01.

3. Locate the second block in the exact position.

4. Validate header, order, fields, type, and syntax of language and URL.

5. Determine whether language is supported.

6. Regenerate notice.txt from type, language, and verification_url.

7. Compare notice.txt byte for byte.

8. Optionally check availability of verification_url.

9. Inspect the presence of presentation artefacts in accordance with PKG-02. Decoding the content of qr.svg is optional for the verifier; if it does so and obtains a URL different from verification_url, it MUST emit RED on the package axis without, for that reason alone, changing the independent disclosure result.

10. Emit disclosure as a separate axis.

17. Separation of results

PTC declaration:        GREEN / RED
Source file:            GREEN / AMBER / RED
Package structure:      GREEN / AMBER / RED
Public disclosure:      GREEN / AMBER / RED

DCL-03 MUST NOT create a global verdict or apply “worst result prevails”. A temporarily inaccessible URL does not make a valid PTC false; a modified notice.txt does not by itself alter the source bytes.

The disclosure axis MUST be shown only when PTC DISCLOSURE exists or when a recognizable disclosure attempt is detected, such as a malformed block, public_notice in manifest.json, or entries under PUBLIC_NOTICE/.

When no disclosure block or artefact exists, the interface MUST omit this axis. It MAY show, outside the traffic-light system, the neutral indication “No public notice”. This omission does not create a fourth state and does not constitute AMBER.

AMBER is reserved for recognizable disclosure attempts that cannot be fully resolved, such as a well-formed but unsupported language or an unavailable external check.

PART IV · Normative notice.txt

18. Function

PUBLIC_NOTICE/notice.txt is the only derived artefact whose byte-for-byte equality forms part of the disclosure axis. It is generated exclusively from type, language, and verification_url.

19. Exact serialization

Without verification_url:

<TITLE>
LF
<BODY>
LF

With verification_url:

<TITLE>
LF
<BODY>
LF
<URL_LABEL>: <verification_url>
LF

UTF-8 without BOM.

Exactly one blank line between title and body.

When a URL exists, exactly one blank line between body and verification line.

No trailing spaces.

Exactly one final LF.

profile, type, language, date, hash, and technical explanations are not added.

PART V · Presentation and integration with PKG-02

23. notice.html and notice.svg

They are presentation artefacts, not cryptographic authorities.

A conformant generator MUST display the same semantic title and body as notice.txt.

MAY change design, typography, dimensions, accessibility, and styles.

A verifier MUST NOT require byte-for-byte equality or turn the disclosure axis red because of visual differences.

An obvious detected contradiction MAY be shown as a package or presentation warning.

24. qr.svg

Generated only when verification_url exists.

A conformant generator MUST encode only the exact verification_url string.

MUST NOT introduce text, identifiers, hashes, or tracking data inside the QR.

The absence of a QR when a URL exists is a package incident under PKG-02.

Changing the bytes or style of the QR does not by itself invalidate the disclosure axis.

If a verifier chooses to decode qr.svg and obtains a URL different from verification_url, it MUST emit RED on the package axis because of contradiction with an authoritative artefact. The disclosure axis continues to depend on the protected block and notice.txt.

25. PUBLIC_NOTICE/ folder

PUBLIC_NOTICE/
    README.txt
    notice.txt
    notice.html
    notice.svg
    qr.svg       # only with verification_url

The presence of PTC DISCLOSURE, public_notice in manifest.json, and PUBLIC_NOTICE/ MUST be coherent in accordance with PKG-02.

Coherence between files present in PUBLIC_NOTICE/ and paths declared in public_notice is governed by PKG-02.

Additional files do not by themselves alter the disclosure axis. A safe additional entry may produce AMBER on the package axis, and a dangerous, ambiguous, or contradictory entry may produce RED on that axis, in accordance with PKG-02.

26. public_notice object

{
  "public_notice": {
    "profile": "disclosure-notice-v1",
    "readme_path": "PUBLIC_NOTICE/README.txt",
    "notice_path": "PUBLIC_NOTICE/notice.txt",
    "html_path": "PUBLIC_NOTICE/notice.html",
    "svg_path": "PUBLIC_NOTICE/notice.svg",
    "qr_path": "PUBLIC_NOTICE/qr.svg",
    "verification_url": "https://example.org/declaration"
  }
}

qr_path and verification_url appear together or are omitted together. The manifest routes; the protected block determines type, language, and URL.

PART VI · States, URL, and limits

27. Disclosure-axis states

The total absence of disclosure is not represented in this table: the axis is not instantiated. The table applies when a block or recognizable disclosure attempt exists.

Status

Condition

Minimum message

GREEN

Conformant block, supported language, and exact notice.txt.

The public notice matches the protected declaration.

AMBER

Well-formed but unsupported language.

Notice language not supported by this version.

AMBER

Conformant URL but unavailable or not checkable.

The declared address could not be confirmed now.

AMBER

The device cannot read notice.txt or check the URL.

Incomplete disclosure check.

RED

Mandatory field absent, duplicated, out of order, or invalid type.

The disclosure block is not conformant.

RED

verification_url exists but does not satisfy the syntax.

The declared address is not a conformant HTTPS URL.

RED

notice.txt is missing or differs byte for byte.

The normative notice does not match the protected declaration.

RED

Block duplicated, isolated, or composed without FRS-01.

Disclosure composition not permitted.

RED

public_notice or PUBLIC_NOTICE/ entries exist, but there is no protectable PTC DISCLOSURE.

There is a notice attempt without the canonical declaration that must govern it.

28. URL availability

The network check is optional.

CORS, offline mode, DNS, TLS, or temporary failure MUST NOT invalidate the PTC.

An HTTP response does not demonstrate that the page displays the correct package.

A reserved URL may remain amber until publication.

A 301, 302, 307, or 308 response to a different destination is recorded as availability information or as operational AMBER. The redirect does not modify the protected object or the disclosure axis.

The final destination of a redirect MUST NOT silently replace verification_url or be considered cryptographically equivalent.

Validator MUST NOT assert future persistence.

29. Effective exposure

Limit not resolvable by the package

DCL-03 can demonstrate that a protected notice existed and that notice.txt represented it correctly. It cannot demonstrate that a platform, institution, or person displayed it at the required time.

30. Platform-transformed copies

A platform may recompress an image or transcode a video. FRS-01 identifies the preserved original; the notice and URL maintain public traceability. Validator MUST NOT assert that the bytes reproduced by the platform match the original unless independently checked.

31. Security and privacy

verification_url is made public within the block, notice.txt, HTML, SVG, and QR.

The URL SHOULD NOT contain secret tokens, unnecessary personal data, or temporary identifiers.

HTML artefacts MUST NOT include scripts, trackers, or remote resources by default.

The QR MUST NOT encode anything other than the URL.

The URL check SHOULD avoid sending the source file or PTC to third parties.

32. Compatibility

A newer Validator MUST continue to verify packages without disclosure.

A verifier that does not know disclosure-notice-v1 may verify the PTC as text, but not the disclosure axis.

An unknown profile produces disclosure AMBER, not automatic PTC invalidity.

Future changes to HTML, SVG, or QR libraries must not turn old packages red.

Future disclosure for ordinary textual content will require another profile and does not modify v1.
